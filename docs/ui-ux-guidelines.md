# UI/UX 設計注意事項

這份文件定義 `realtime_map_notice` Web App 的前端設計原則。這個專案的畫面核心是「地圖上的即時資訊」，所以 UI/UX 的目標不是做得花俏，而是讓使用者在短時間內看懂附近發生什麼、是否需要立刻注意、以及下一步可以做什麼。

## 設計目標

- 地圖永遠是主角，事件資訊不能遮住主要地圖內容。
- 使用者可以在 3 秒內判斷附近是否有重要事件。
- 一般事件保持低干擾，緊急事件要明顯但不能造成恐慌。
- 定位、插旗、通知三個核心流程要能在 Demo 中穩定呈現。
- 桌機瀏覽器與手機瀏覽器都要可用，因為實際使用者可能拿手機打開 Web App。

## 主要畫面

### 地圖主畫面

地圖主畫面建議採用全螢幕布局，讓使用者一進入系統就看到校園或街區狀態。

需要注意：

- 地圖上方或下方可以放輕量工具列，但不要使用大型介紹區塊。
- 使用者目前位置要清楚，例如藍色圓點或帶有方向感的標記。
- 事件標記要依類型或嚴重程度區分，但顏色數量不要過多。
- 地圖縮放、拖曳與點擊插旗要直覺，避免和表單操作互相衝突。
- 地圖載入中、定位中、無法定位時都要有明確狀態。

### 事件列表

事件列表可以作為地圖的補充資訊，建議用底部抽屜或側邊面板呈現。

需要注意：

- 列表預設顯示附近事件，不要一次塞太多全區事件。
- 每筆事件至少顯示標題、類型、距離、時間與嚴重程度。
- 緊急事件排在一般事件前面。
- 使用者點擊列表項目後，地圖應移動到對應標記。
- 列表可以收合，避免長時間遮住地圖。

### 插旗表單

插旗流程要短，適合臨時快速回報。

建議欄位：

- 事件類型：座位、人潮、活動、遺失物、交通、安全、其他。
- 嚴重程度：一般、重要、緊急。
- 標題：短文字，讓地圖標記和通知容易辨識。
- 說明：可選填，補充細節。
- 位置：預設使用目前地圖點擊位置，也允許使用目前定位。

需要注意：

- 表單不要太長，Demo 時最好 20 秒內可以送出一筆事件。
- 緊急事件送出前可加一次確認，避免誤發。
- 送出成功後要立即在地圖上出現標記。
- 送出失敗時要明確提示，例如 API 連線失敗或定位不可用。

## 通知設計

### 一般事件通知

一般事件不一定需要彈出強烈通知，可以在事件列表或地圖標記中更新。

建議：

- 使用低干擾提示，例如列表新增、標記閃爍一次。
- 不要每一個一般事件都跳出大型 Banner。
- 避免頻繁通知造成使用者關閉系統。

### 緊急事件通知

緊急事件是本專題亮點，必須在 500 公尺內使用者畫面上清楚呈現。

建議：

- 使用頂部或底部 Banner 顯示事件標題與距離。
- Banner 需要有明確的「查看位置」動作，點擊後地圖移動到事件座標。
- 顯示距離，例如 `距離你 180m`。
- 顯示發生時間，例如 `剛剛`、`2 分鐘前`。
- 使用明顯但克制的顏色，例如紅色用在緊急事件，不要整個畫面大量閃爍。
- 使用者可以關閉 Banner，但事件仍保留在列表中。

## 定位與權限

瀏覽器定位是 Web App 的核心，但定位權限常常是 Demo 風險點。

需要注意：

- 第一次進入時提供清楚的「啟用定位」按鈕。
- 使用者拒絕定位時，提供手動選點或預設校園座標。
- 定位中要有 loading 狀態，不要讓畫面看起來像壞掉。
- 定位精度不足時，可以顯示淡色圓形範圍。
- 不要在沒有使用者同意時自動反覆跳出權限請求。

## 狀態與錯誤處理

前端必須處理下列狀態：

- 地圖載入中。
- 定位等待中。
- 定位被拒絕。
- API 連線失敗。
- WebSocket 連線中。
- WebSocket 已斷線，正在重連。
- 事件送出中。
- 事件送出成功。
- 事件送出失敗。
- 附近目前沒有事件。

錯誤訊息建議短而可行：

- `無法取得定位，請改用手動選點。`
- `事件送出失敗，請稍後再試。`
- `即時通知暫時中斷，正在重新連線。`
- `目前 500 公尺內沒有事件。`

## 響應式設計

雖然專題 Demo 可能使用桌機，但實際情境偏向校園行動使用，所以手機瀏覽器也要考慮。

桌機：

- 地圖全螢幕。
- 事件列表可放在右側面板。
- 插旗表單可用 modal 或側邊 panel。

手機：

- 地圖全螢幕。
- 事件列表使用底部抽屜。
- 插旗按鈕固定在右下角。
- 通知 Banner 不可遮住主要操作按鈕。
- 按鈕觸控區域至少約 44px 高。

## 視覺層級

事件嚴重程度建議：

| 嚴重程度 | 用途 | 視覺表現 |
|----------|------|----------|
| 一般 | 座位、人潮、活動 | 中性色標記，低干擾 |
| 重要 | 封路、設備故障、遺失物 | 黃色或橘色標記 |
| 緊急 | 安全提醒、需要附近使用者立刻注意 | 紅色標記與通知 Banner |

事件類型建議使用 icon 輔助，但不要只靠顏色，避免色弱使用者無法分辨。

## 可用性檢查清單

Demo 前至少檢查一次：

- 使用者能在 3 秒內看懂目前位置。
- 使用者能在 20 秒內完成事件插旗。
- 緊急事件通知能清楚顯示距離與事件標題。
- 定位失敗時仍可使用手動座標或預設位置。
- WebSocket 斷線時畫面有重連狀態。
- 地圖標記、通知 Banner、事件列表不互相遮擋。
- 手機寬度下文字不溢出按鈕或卡片。
- 所有主要操作都有 loading、success、error 狀態。
- 一般事件不會造成通知疲勞。
- 緊急事件足夠醒目，但不使用過度閃爍或難以閱讀的效果。

## Demo 設計建議

Demo 畫面要讓教授馬上看懂技術價值：

- 地圖上至少預先準備 3 到 5 個一般事件標記。
- 緊急事件使用不同顏色與 Banner，明確呈現「只有附近使用者收到」。
- 第二個使用者視窗可放在旁邊，方便比較誰收到通知。
- 壓測與 K8s 畫面切換前，先讓觀眾看懂產品情境，再切到終端機展示技術。
